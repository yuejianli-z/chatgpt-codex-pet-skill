# 按出现频率、停留时长和视觉疲劳设计动作

不要给九个格子平均分配视觉冲击。分别记录“设计关注优先级”和“实测屏幕占比”：以下排序是默认美术优先级，不是统计结果，更不保证业务状态持续多久就播放多久。

| 优先级 | 状态 | 设计目标 | 避免 |
|---|---|---|---|
| 1 | 待机 idle | 认可的核心形态；稳定轮廓；呼吸、眨眼等自然微动作 | 反复全身变身、大幅摇晃、闪烁和抢眼道具 |
| 2 | 工作 running | 思考或处理任务；身份稳定、动作克制且有目的 | 疯狂循环；字面跑步；把任务时长当画面时长 |
| 3 | 待查看 review | 成果已完成、等待查看；平静的完成感 | 过度庆祝；把未读成果一律解释成要求回复 |
| 4 | 等待 waiting | 需要批准、输入或决定；清楚面向用户 | 不停挥手催促；与待机无区别 |
| 5 | 失败 failed | 低频异常；短暂可读的失落或恢复信号 | 闪烁警报、破坏性动作、过度夸张 |

招呼、跳跃和左右移动另列为“交互组”。其出现频率取决于用户行为，频繁悬停也可能反复触发跳跃，所以低频假设不是疲劳豁免。幅度适中，并能回到稳定核心姿势。

## 后续展示顺序与图集协议顺序分开

新制作的九动作展示图采用：待机 idle → 工作 running → 待查看 review → 等待 waiting → 失败 failed → 招呼 waving → 跳跃 jumping → 左移 running-left → 右移 running-right。

前五项体现设计优先级；后四项是交互组，并非统计频率排名。`openai_pet_atlas.py` 中 `DISPLAY_ORDER` 用于展示，`ROWS` 用于固定图集协议，严禁混用。十六向仍保持顺时针，不按频率重排。已认可的旧动图不因此重做，也不擅自改既定排版、背景或角色。

## 每个角色先明确，再生成

每种动作记录：来源行为、状态含义、确切姿势、核心／备用形态作用、动作幅度、重复疲劳风险、原尺寸辨识度、回待机衔接，以及已知宿主绑定。见[状态计划](../../templates/zh-CN/state-plan.md)。

- 真实动物：依据物种或个体习惯，不强行套人类姿势。例如狗可通过耳朵和身体表现注意，而非必须摸下巴。
- 已知 IP：核实同版本经典动作，并解释为什么适合该状态；经典动作不自动等于合理等待动作。
- 概念角色：常见动作兜底，但适应现有结构。思考、招呼、请求输入不靠标题也应能区别。
- 多形态：待机和注视默认保留已认可的核心形态，其他形态有意分配；不同形态不自动算身份错误。原有合格的多形态素材不擅自重画或重新分配。不能靠有几行就推算 80/10/10 屏幕占比。
- 重复姿势：一个捧肚子的默认动作可以有角色特点，但不能九组都只捧肚子，否则状态语义消失。

必须审查“待机→每组动作→待机”，包括宿主支持的中断、回退、落脚点与比例跳变。高曝光设计实际看满 30 秒和 60 秒，记录观看者和现象；生成 GIF 或运行评分不算看过。不要为了增加备用形态出现次数，擅自在待机或注视中塞入反复强变身；那是独立视觉设计变化，需要明确认可。

## 触发证据单独记录

已收到的用户观察：桌面宠物鼠标移入触发跳跃，左右拖动播放对应方向动作，首次显现播放招呼；页面顶部 dot 随周围鼠标切换十六向注视。这些是对应客户端的用户实测报告，不是所有版本的通用承诺，也不能推出两处都调用全部九行。

每条绑定记录 `surface`、`client_version`、`event`、`animation`、`evidence_kind`（unknown／user_observed／source_verified／actual_client_test）、来源与限制。版本未知写“未记录”，不自动泛化。能观察时分别记录业务状态、请求的动画、实际显示帧及停留占比。参照[运行状态证据](runtime-state-evidence.md)和[制作安装流程](openai-production.md)。

# Multi-form design and capability preflight

## R06 — One identity, one atlas, supported event mapping

Distinguish multiple forms of one identity, multiple separate companions, an offline three-form demo, a designed transformation inside an action row, and runtime automatic transformation. Completing one does not establish the others. If the request is one multi-form companion, three pets or three parallel showcase boards are not substitutes.

Record each form's approval provenance, invariants, actor/accessory ownership, per-state form mapping, main-form start/end anchors, fixed frame budget, transition source indices, loop evidence, and interruption evidence. An example adapter has one atlas with nine action rows (57 frames) and 16 directions; do not hide a second form set in unused transparent cells or pretend a description field executes logic.

Where supported, keep routine and directional states in the main form; map a temporary alternate form to a specific existing event, beginning and ending in the main form. Preserve the state's meaning: a jump still takes off and lands, a failure still reacts. If five frames cannot fit both transformation and the core action, retain the failure or revise scope; do not invent frames or omit the core action. Separate alternate idle demos do not establish automatic host morphing.

Desired main-form prevalence is an intention until measured. Atlas cell counts and offline video proportions are not host probabilities. Do not promise 80/10/10, cooldowns, dwell times, background scheduling, or seamless arbitrary interruption without actual contract and runtime evidence.

### Capability evidence matrix

| Capability | Required evidence | When unknown |
|---|---|---|
| Fixed state/frame budget | Current host schema | Do not claim importability |
| Persistent form variable | Actual API and runtime test | Design within one row, returning to main form |
| Random probability/cooldown/timer | Settable field and observed behavior | Keep prevalence an intention; invent no scheduler |
| Custom events/branches | Host event contract | Use existing state semantics or separate demo |
| Blending/interruption | Actual entry/hold/exit transition tests | Label offline cuts as risks; seamless runtime unproven |

## R14 — Verify available tools before promising output

This package is a portable assistant method with diagnostic code, not a model, generation service, app installer, or complete board renderer. Check tools and transmission authorization individually:

- Text only: deliver a specification or plan; do not claim images were generated or viewed.
- Image reading: inspect input identity; private-photo reverse search needs its own authority.
- Image generation/editing: verify an actually available, user-selected provider and applicable cost/data limits. No provider or credentials are bundled.
- Python 3.10+ and Pillow: support diagnostics and original geometric test fixtures. Moving rectangles test pixels, not biological action, identity, or comfort.
- ffmpeg: optional encoding/probing dependency. Use a project-owned or lawfully available renderer separately; there is no bundled complete character-board renderer.
- Actual native-size playback: required for human 30/60-second viewing; decoding cannot substitute.
- Host import/upload: optional separate adapter. Follow current official instructions only when tools are available; installing this skill grants no platform API or pet. Do not redistribute unknown-license platform implementations or invent download links.

Use the repository's documented preflight/test commands to establish machine readiness. Report each capability as available, unavailable, or untested; successful fixture tests do not prove character production or host support.

Read [runtime state evidence](runtime-state-evidence.md) before interpreting activity labels, assigning frequent forms or claiming measured occupancy.

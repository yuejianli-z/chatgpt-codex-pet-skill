# Operational workflow

English is canonical; the [Chinese guide](../zh-CN/workflow.md) carries the same requirements. Use this workflow to plan and review a companion project; asset rights and host acceptance are checked separately.

## 0. Verify the destination before production

**R15 — Platform foundation.** Before committing style or animation budgets, identify the target product, client/version and accepted asset type. Record current authoritative format/state requirements and evidence; separate host hard constraints, mandatory production gates, heuristic diagnostics, preview settings and observed runtime. A missing capability is **unknown**, not supported. Concept-only work can proceed with an explicit integration gap; stop dependent import/activation claims. Read [platform foundation](platform-foundation.md) and complete its checklist before integration.

A local quality error is not evidence of a server rejection or content prohibition. Preserve approved artwork and the original failed report; classify the cause before editing. Never change a bundled gate, remove report fields, or fill intentional negative space merely to obtain a pass. Required failing gates remain blocking until resolved through a supported route. A diagnostic false-positive reproduction does not certify the actual character. Track displayable, format/production-ready, installed and runtime-accepted separately, tied to the exact artifact and client version.


## R01 — Accept ordinary inputs and preserve provenance

Start from a name, original description, phone photo, low-resolution meme, video, multiple references, or an already approved atlas. Do not demand a professional reference sheet. Preserve the original input as the test input; better research references supplement it rather than silently replacing it. Resolve consequential name/version ambiguity with actual viewed references, asking one focused question only when necessary. A transliteration is not an official English name.

Record input type, identity category (personal pet, existing character, meme/avatar, original, private or unknown), source/version, what was actually visible, and missing views. Distinguish official, community-maintained, fan adaptation, user-supplied, and inferred evidence. Unknown provenance stays unknown. Private photos are not automatically authorized for third-party reverse search. A missing back view is an inferred design, requiring permission to invent where needed, not observed anatomy.


For an established public character, default to at least three useful, actually inspected references from the same version, covering distinct identity/structure/action evidence rather than duplicate images. If fewer are available, disclose the gap and limit claims; do not invent evidence or silently substitute versions. This quota does not apply to private photos, original concepts or genuinely unavailable public references.

## R03 — Select style before expanding production

For a new or materially changed style, default to three distinct controlled samples: same identity, pose, expression, camera, and outfit semantics; vary style. Show enlarged comparisons and actual target display size. If host size is unknown, show 64/96/128-pixel-high calibration previews labeled as calibration, not host measurements. High-resolution masters do not require dense detail.

Obtain the specific style choice before batching states or directions. Reuse an unchanged approved baseline without asking again. The only substitution for a new style choice is an explicit waiver covering this character and this style selection; broad autonomy does not waive a later specific style gate. Record approval scope separately for style, identity, outfit, pose, and final delivery. Material approval does not approve the face, proportions, or outfit. Preserve original-proportion CG, realistic pets, ink, stickers, or soft 3D when chosen; do not default every character to a large-headed toy.

## R04 — Freeze the latest relevant approved baseline

Track reference version/hash, approval scope, and user evidence in private project records. Resolve conflicts using the approval timeline relevant to the current task; an earlier installed version is not automatically authoritative. Reopen same-version references when evaluating candidates. Compare near-matching views without stretching width and height independently; state normalization basis, landmarks, occlusion, and uncertainty. Face/core-component close-ups and native-size whole-character views are separate checks.

For action-only repairs list permitted changes and protected identity features. Do not change chin, proportions, eyes/mouth, outfit, or accessories to make motion easier. Every changed cell requires the identity gate in [quality](quality.md); unchanged-cell counts cannot approve changed cells.

## R05 — Work in two stages with bounded iteration

After platform verification, Stage 1: identify and research → define invariants and intended feeling → style samples → one approved baseline. Stage 2: recheck the host contract → inspect existing rows and build a source-tiered action bank → propose one justified performance per state for user inspection → compile concrete briefs → review representative whole-cycle semantic contrasts → expand only approved affected states/directions → inspect final exports → deliver with limitations. Static requests may end after Stage 1.

Read [source-led action design](action-design.md). A semantic redesign does not reopen approved appearance. Present the action map before broad art changes, preserving good old actions and historical prompts.

Consolidate user judgments around reference/identity, image baseline, and representative actions when needed. These are a default maximum-style grouping, not three mandatory approval rounds. Reliable identity evidence can make the reference board informational; existing approvals need not be repeated. Ask again only for a material identity, scope, or permission change.

Before each experiment write one main defect, a causal hypothesis, protected features, observable success conditions, and a sample budget. Default to at most two targeted local attempts per hypothesis; this is a cost-control budget, not a quality threshold. If neither helps, change evidence, pose constraints, composition/modeling, or editing route. Confirm material scope/cost changes. Record defect → hypothesis → bounded change → observed result → retain/revert. Preserve the best approved version and failures. No output or unviewed output remains unverified.

## R07 — Deliver the requested completeness, not an inflated status

Read the current host schema. The dated Pets v2 adapter has nine tracks / 57 action frames plus 16 gaze samples, distinct from four desktop business statuses. Body views are presentation requirements when requested, not host states. Compose real action loops, one-character gaze and the requested static views in a single board, with concise bilingual labels and no dense footer. Choose dimensions from the latest verified layout. Deliver a representative overview and private sources alongside the animation. Unseen view details remain disclosed inference. [Identity and presentation](identity-and-presentation.md)

Keep masters/source atlases and provide lightweight chat previews. Check preview coverage, scale, source-index timing, and tail holds against the master, not just file readability. If previews are too heavy, produce lighter derivatives while preserving masters. A preview does not replace an importable atlas; uploading is not runtime validation; installing a skill does not create or install a companion.

## R12 — Keep permission and release boundaries explicit

Track output level (concept, full showcase, importable asset, installed/runtime-tested) independently from publication permission. Keep private photos, character artwork, private identifiers, historical prompts, credentials, and unclear-license assets outside a redistributable candidate. Code licensing does not grant character/art rights; user acceptance of IP risk is not rights-holder permission. Do not promise copyright clearance. No publication, upload, installation, or external transmission follows merely from preparing project files.

Use [quality](quality.md) and [multiform](multiform.md) for execution gates and evidence limits.

For a requested large board, use [panel labels](../../templates/en/action-board.md): meaning, selected action, source route/adaptation, rationale/distinction, exact-surface trigger evidence or unknown, and key-pose versus complete-sequence coverage. Gaze samples get their own direction labels and do not count as additional task states.

Preserve the requested output format. When a large animated board is requested or established by the supplied reference, do not finish with a static pose sheet or still-image slideshow. Mark interim key-pose sheets as previews; verify actual within-state source motion in the final encoded animation before claiming completion.

When the user authorizes an ordered character series, proceed in that order one character at a time. Reuse layout and label conventions, not unreviewed character motions. Check each actor’s identity, three-route source selection, semantic contrasts, actual frames, text, and final encoding before presenting it. Later authorization supersedes an earlier sample-approval hold only within its stated scope; it does not certify an unfinished layout or permit installation/publication.

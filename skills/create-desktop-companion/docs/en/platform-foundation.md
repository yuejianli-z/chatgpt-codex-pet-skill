# Platform foundation and acceptance evidence

Verify the destination first. A three-dimensional appearance does not establish support for a 3D mesh, rig, physics or SVG. Obtain the actual accepted asset contract; a sprite renderer may only accept a raster atlas. Product names and clients are not interchangeable.

## Evidence classes

| Class | Evidence needed | What it does not establish |
|---|---|---|
| Host hard constraint | Current authoritative schema or a direct validation result for this exact asset/version | Natural motion or identity |
| Mandatory production gate | Applicable current workflow requirement and unmodified result | Server rejection, legal status or content policy |
| Heuristic diagnostic | Measurement, source comparison and reviewed failure region | Defect certainty or an automatic exemption |
| Preview behavior | Export timeline, decoded frames and settings | Client scheduling, frame rate or interruption blending |
| Observed runtime | Actual target client, exact asset/version and recorded observation | Every other client/version or unobserved state |
| Content restriction | Explicit applicable service result | Copyright ownership or a general ban on this visual style |

Record source, version/date, scope and supported / unsupported / unknown for each capability. Unsupported means affirmative evidence of absence; unknown means not established. Do not infer random idle selection, dwell probabilities, custom states, configurable FPS, event throttling, live 3D, gaze interpolation or transitions from a demo or successful upload.

## Before committing a production budget

- Destination product/client/version and intended display size; accepted file types, dimensions, alpha behavior, maximum file size and grid/layout.
- Required state keys, frame counts/order, direction catalog and coordinate convention; distinguish state names from artistic meanings.
- Which requirements are authoritative, which are dated snapshots, and which need rechecking. Do not universalize example counts.
- Frame durations, looping versus one-shot behavior, dwell length, entry/exit behavior, interruption rules, gaze priority and error fallback: record evidence or unknown individually.
- Supported import, update, activation and rollback route; current selected identity and preserved baseline. No live mutation merely to discover the format.
- Tool access and supported validation route. Continue useful concept/preview work when integration is blocked, labeled accordingly.

## Four independent delivery claims

These are evidence dimensions, not an automatic ladder. Successful upload does not repair a failed gate, and installation is not runtime acceptance.

1. **Displayable:** the exact preview can be opened/decoded and its scope is labeled. Static or partial examples remain clearly labeled.
2. **Format/production-ready:** exact final asset meets the current target contract, every applicable mandatory gate passes, and a supported structural eligibility check exists. Creation/content acceptance remains pending until separately verified; this label never promises that installation will succeed. If no such route exists, state “candidate; eligibility unverified.”
3. **Installed:** the authorized operation has an affirmative result for the exact artifact, plus selection/activation readback if claiming active. A prepared file or request submission is insufficient.
4. **Runtime-accepted:** actual target-client observations cover the stated test scope, with unresolved defects and untested states exposed. Offline playback cannot satisfy this dimension.

Revalidate affected claims after any byte, gate, adapter or client-version change. Record unknown instead of promoting status. Use `scripts/check_platform_claims.py` for record-consistency checks; it cannot authenticate evidence or run the host.

## State, timing and interruption checklist

For every required state: trigger/evidence, actual source identity, observed duration and frame timing, loop/one-shot semantics, natural contact/pose/velocity seam, native-size readability, and missing coverage. For sustained states, perform the 30/60-second viewing checks in [quality](quality.md); do not infer natural dwell frequency from a staged test.

Test supported entry→hold, hold→exit, exit→idle, idle↔working, and state↔gaze switches at early/middle/late phases. Also check repeated triggers, short-lived tasks, interruption during a one-shot and failure/recovery where supported. Record unsupported or inaccessible trigger paths without inventing them. For multiform assets test form interruption explicitly. Label offline hard-cut simulations separately from actual client behavior. Preserve registration, silhouette and facial identity throughout.

## Diagnose before changing approved art

Keep the original report and asset hash. Identify whether the issue is structure, extraction, visual defect, heuristic suspicion, service restriction or actual runtime. Compare the affected source region before/after extraction on light/dark backgrounds. A reproducible false positive demonstrates a diagnostic limitation, not that every alert in the character is false.

A useful synthetic regression set contains: an open U-shaped gap connected to the background; a deliberately closed ring; an accidental internal horizontal seam; a background-connected crack; narrow/antialiased channels; and disconnected intended versus broken components. Open gaps must not be mislabeled as enclosed holes. Conversely, background connectivity alone must not clear a real crack, and an enclosed ring is not necessarily damage. Real seams, broken silhouettes and missing body parts must remain detected or require review. Test 4/8 connectivity and alpha-threshold sensitivity.

Do not alter a required bundled checker, erase failing fields, weaken thresholds or fill intentional spaces just to pass. Diagnostic supplements are not gate overrides. Repair a proven extraction error only by recovering source-supported pixels, then rerun all gates and identity checks. If the gate rejects intentional approved art and no supported exception exists, preserve the design, report the compatibility blocker and retain preview-only delivery. A maintenance/appeal route may be proposed; it is not already implemented or permission to contact a third party.

Read [runtime state evidence](runtime-state-evidence.md) before interpreting activity labels, assigning frequent forms or claiming measured occupancy.

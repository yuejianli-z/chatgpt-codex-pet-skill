## Feature applicability before generation

Record each actor separately using `templates/feature-applicability.example.json`: `has_face` is true/false/null; `features` records observed availability with the same values. Each motion cue names its `actor_id`, readable `signal`, and `required_features`. Require explicit true for every required feature; unknown is not available. For `has_face: false`, never require pupils, nose tip, mouth, eyes or eyebrows. Do not borrow anatomy from another actor in a compound subject. Use an approved structural cue such as body axis only if the source supports it.

Run `python scripts/check_feature_applicability.py templates/feature-applicability.example.json`, then inspect the actual generation instructions for the same constraints. The checker validates structured plans only, cannot parse arbitrary prose or inspect artwork, and grants no upload/installation approval.

Canonical facial feature keys reserved by the checker are `face`, `face_surface`, `eyes`, `pupils`, `nose`, `nose_tip`, `mouth`, `eyebrows`. Map equivalent labels to these keys before validation; arbitrary synonyms are not semantically classified. Supported structural keys are `body_axis`, `head_offset`, `connected_arm`, `torso_lean`, `support_point`, `tail`, `wing`, `wheel`, `pointer`. Unknown keys fail even when declared true. Do not map an incompatible feature to an unrelated key merely to pass; if the vocabulary cannot represent the character, report the schema gap and review separately.
